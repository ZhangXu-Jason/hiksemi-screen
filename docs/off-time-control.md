## 一、客户端契约（逆向自 `index-be27a12a.js`）

相关函数：`getCloseScreenPeriod()` / `setCloseScreenPeriod()` / `getScreenConfig()` / `setAutoScreen()`

### 1.1 两个 REST 接口（均 `/rest/1.1/config`）

| 方向 | URL | 响应（客户端读取字段） |
|---|---|---|
| 读 | `?action=get_off_time&cmdfrom=devsub` | `res.code===0 ? res.xp_time : -1` |
| 写 | `?action=set_off_time&xp_time={n}&cmdfrom=devsub` | `res.code===0` 视为成功 |

### 1.2 ★★★ 关键坑：字段名是 `xp_time`（标量），不是 `off_time`（数组）

```js
// getCloseScreenPeriod()
i && i.code === 0 ? e(i.xp_time) : e(-1);      // ← 读的是 xp_time
```

旧中间件返回的是 `{"code":0, "off_time":[]}` —— 客户端拿 `res.xp_time` 得到
`undefined` → UI 永远显示 `--` → 用户看到"设置不生效"。

**正确响应：`{"code": 0, "xp_time": <秒>}`**

### 1.3 合法档位（客户端 `AUTO_CLOSE_LIST`）

| 显示 | `xp_time`（秒） |
|---|---|
| 30 秒 | 30 |
| 1 分钟 | 60 |
| 2 分钟 | 120 |
| 5 分钟 | 300 |

### 1.4 客户端行为

- **只发偏好**：`setAutoScreen(e)` → `setCloseScreenPeriod(e)` → 成功则更新本地 `autoCloseScreen`。
- **不做熄屏动作**：客户端全程没有 `fb0` / `blank` 逻辑 ——
  **真正黑屏必须由服务端做**。

## 二、★ 熄屏动作由服务端实现（照抄原厂）

原厂 `config_callback` 的 `set_screen_power()`：

```bash
# 亮屏
echo 0 > /sys/class/graphics/fb0/blank
# 黑屏
echo 1 > /sys/class/graphics/fb0/blank
```

- 值：`0`=亮 / `1`=黑
- 屏幕亮度（另一回事）：`/sys/devices/pci0000:00/0000:00:02.0/drm/card0/card0-DSI-1/intel_backlight/brightness`

### 2.1 ★★★ 但原厂路径在飞牛OS 上不能照抄（本机实测踩坑）

原厂固件里小屏就是 `fb0`，所以它写死了。**飞牛OS 上不是这样**：

- 本机有**多个 `fb*` 设备**（实测 3 个），`fb0` 很可能是 HDMI/虚拟输出，
  **不是小屏**。
- 更坑的是：**写 `fb0/blank` 会"成功"——不报错、回读值也变成 1，
  但小屏纹丝不动。** 因为那是另一块屏幕的 framebuffer。
- 于是日志里出现 `熄屏（已写入）`、`黑屏中=True`，**而屏幕依旧亮** —— 
  内部状态与硬件彻底脱节。

**正确做法（中间件已实现，五级策略）：**

| 优先级 | 手段 | 说明 |
|---|---|---|
| 1 | **按 `virtual_size` 锁定小屏 fb** | 分辨率 `376×960` / `960×376` 是**物理事实**，最可靠；命中即只写它 |
| 2 | 缓存路径 | 上次成功的路径（且非分辨率候选时） |
| 3 | 遍历所有 `fb*/blank` | 无分辨率匹配时的退化路径 |
| 4 | **背光通道** | `/sys/class/backlight/*/brightness = 0`（原厂亮度路径，值域 0–96000） |
| 5 | **DPMS 通道** | 写 `/sys/class/drm/cardN-XXX/dpms = Off`（DRM 层面关屏，对 DSI 有效） |

> **判据速查**：小屏分辨率是 **376×960**（竖装）或 **960×376**。
> 用 `cat /sys/class/graphics/fb*/virtual_size` 一眼就能认出哪个是小屏。

```bash
# 一条命令找出小屏对应的 fb（认虚拟分辨率，不认编号）
for fb in /sys/class/graphics/fb[0-9]*; do
  echo "$(basename $fb): $(cat $fb/virtual_size 2>/dev/null)  $(cat $fb/name 2>/dev/null)"
done
# 看到 376,960 或 960,376 的那个就是小屏
```

### 2.2 ★★★ 真相：X 在跑时，`blank` 为什么无效（真机诊断定论）

第三轮修复改用"分辨率锁定 fb"，**仍然不黑**。真机诊断给出了决定性证据：

```
【1】只有 fb0 一个，virtual_size=376,960   ← 就是小屏，路径没错！
【7】写 fb0/blank=1 → 回读=1               ← 写入成功，但屏幕不黑
【8】背光 brightness 68160 → 0 → 68160    ← ★ 这个通道物理可用！
【3b】/tmp/.X11-unix/X0 存在               ← 程序跑在 X 上
```

**根因**：
> 程序跑在 X server 上，**X 通过 DRM/KMS 直接把画面提交给显示硬件**。
> 而 `/sys/class/graphics/fb0/blank` 只作用于 **framebuffer console 层**
> —— 它管不到 X 已经渲出来的画面。
> 所以写它不报错、`fb0` 的状态位也变了，**但屏幕上的 X 画面照旧**。

原厂能用是因为它的 X 配置/驱动后端不同；在飞牛OS 这套组合下不行。

**⇒ 最终方案：背光优先。**

| 通道 | 手段 | 本机实测 |
|---|---|---|
| **P1 背光（首选）** | `backlight/*/brightness = 0` + `bl_power = 4` | **✅ 有效**（诊断【8】验证） |
| P2 DPMS | `drm/cardN-XXX/dpms = Off` | 未验证（备用） |
| P3 blank | `fb0/blank = 1` | ❌ X 下无效（聊胜于无） |

**★ 背光看门狗（必须）**：背光写到 0 后，若中间件崩溃/被 kill 而不还原，
**屏幕会永久全黑**，用户会以为设备坏了。故中间件注册了
`atexit` + `SIGTERM/SIGINT/SIGHUP` 钩子，退出时强制还原背光。

## 三、中间件实现

### 3.1 状态层 `OffTimeState`
- 持久化：`/var/lib/hiksemi-sub/off-time.json`（首选），兜底 `<脚本目录>/.off-time-state.json`
- 线程安全 + mtime 感知外部改动
- `_normalize_off_time()`：把任意输入**夹到最近合法档位**（30/60/120/300），
  非数字 → 默认 120

### 3.2 读 builder `build_off_time`
返回 `{"code": 0, "xp_time": N}`（修复了 `off_time` 数组的契约 bug）。

### 3.3 写 resolver `resolve_off_time_write`
读取 `?xp_time=`，落盘并返回字段值 `0`（避免 `{"code":{"code":0}}` 嵌套）。

### 3.4 ★ 空闲监视 `start_idle_monitor`（后台守护线程）
```
启动：记录【监视启动时刻】作为计时基准（不是模块导入时刻！）
循环（用 select 等待输入，最长 0.5s）：
  ├─ 检测输入活动（/dev/input/event* 或 xprintidle）
  │   有活动 → 计时重置；若已黑屏 → 写 0 亮屏
  ├─ 档位变化 → 计时重置（避免刚改完档就按旧时长熄屏）
  └─ 空闲 ≥ xp_time → 写 1 黑屏（仅一次，避免反复写）
```
输入来源按可用性回退：
1. `/dev/input/event*`（需 root 读权限）—— **用 `select()` 等待，有输入立即唤醒**
2. `xprintidle`（装了 x11-utils 时）
3. 都没有 → **只保存设置，不实际熄屏**（日志明确提示）

#### ★★★ 屏幕控制三级策略（`_screen_set`）

熄屏不只是"写个文件"。本机踩过 **「写成功但屏幕不黑」** 的坑，所以实现成三级：

```python
_screen_set(blank)          # True=黑屏, False=亮屏
  ├─ L1 写【已验证】缓存路径 → _write_blank() 回读确认
  ├─ L2 未命中 → 遍历所有 fb*/blank，逐个写 + 回读，命中即缓存
  └─ L3 全部无效 → 走背光通道（brightness=0 / 还原）
返回 True 表示【确认生效】，不再是"没抛异常"
```

**`_write_blank()` 的核心：写完必须回读。**

```python
def _write_blank(path, blank):
    val = "1" if blank else "0"
    with open(path, "w") as f: f.write(val)     # 写入
    got = _read_blank(path)                     # ★ 回读
    if got is not None and got != val:
        log(f"✗ blank 写入【未生效】({path}): 写 {val} 但回读为 {got}")
        return False                            # ★ 不许谎报成功
    return True
```

**选屏打分（`_score_blank_path`）**：`DSI` 100 分 > `eDP/LVDS` > 无信息按编号 > 
`HDMI/VGA` **-50 分**（明确不是小屏）。

> ⚠️ **绝不死认 `fb0`**。本机 `fb0` 写 blank **不报错、回读也变**，但屏幕不黑——
> 那是别的 framebuffer。必须按连接器/分辨率挑。

#### ★★★ 熄屏失败时**不得**标记 `blanked=True`

```python
if ok:
    _IDLE["blanked"] = True      # 确认黑了才标记
else:
    _IDLE["blanked"] = False     # ★ 没黑就保持 False，下轮继续重试
    _IDLE["blank_fail_warned"] = True
```

否则内部以为"已黑屏"、实际还亮着 → **状态永久脱节，且再也不会重试熄屏**。
这正是本机日志 `黑屏中=True` 而屏幕亮的直接原因。

#### ★★★ 计时基准的三个坑（真机日志暴露）

| 坑 | 错误做法 | 正确做法 |
|---|---|---|
| **基准时刻** | `_IDLE["last_active"]` 在**模块导入时**初始化 → 进程起来就"已空闲很久" → **一启动就秒黑屏** | 在 `_idle_loop` 开头显式 `_IDLE["last_active"] = time.time()` |
| **改档不重置** | 改档只写文件，计时继续走 → 刚设完 30s 就立刻黑屏 | `set_off_time` 重置计时；`_idle_loop` 内也检测档位变化并重置 |
| **噪声当活动** | 「读到任何字节」都算活动 → 触摸屏持续发 `EV_SYN` 噪声 → **`已空闲` 永远是 0、熄屏永远不触发** | **解析 `input_event`，只认 `EV_KEY`/触摸坐标**（见下） |

真机日志实录（暴露第 2 个坑）：
```
01:36:37  检测到输入 → 亮屏          ← 计时基准 01:36:37
01:36:41  set_off_time → 30s         ← 改档，但未重置
01:37:20  空闲 30s ≥ 30s → 熄屏      ← 从 01:36:41 起算，已超时
```

#### ★★★ 噪声过滤（第 3 个坑，最隐蔽）

真机日志（新版）暴露：**熄屏不及时 / 要等很久**。心跳显示 `已空闲=0s` 反复出现：
```
01:48:20  心跳: 档位=30s 已空闲=0s     ← 启动后 22 秒
01:48:23  心跳: 档位=30s 已空闲=0s
01:48:26  心跳: 档位=30s 已空闲=0s
01:48:45  心跳: 档位=30s 已空闲=11s    ← 偶尔才累积
```

**根因**：`/dev/input/event*` 里有设备**持续上报 `EV_SYN` 事件**（触摸控制器的帧同步/心跳/悬浮噪声），而旧实现「读到任何字节都算活动」→ `last_active` 被无限刷新 → 空闲计时永远起不来。

**修复**：解析 Linux `input_event` 结构，**只认真实操作**。

```python
# struct input_event: time(16B) + type(u16) + code(u16) + value(s32) = 24B
# 只认：
#   EV_KEY(1)                            → 按键/触摸按下抬起
#   EV_ABS(3) 且 code ∈ 触摸坐标轴 且 value != 0  → 手指移动
#   EV_REL(2) 且 value != 0              → 鼠标移动
# 忽略：
#   EV_SYN(0)  ← ★ 噪声主源，帧同步标记，本身不代表操作
#   EV_MSC(4) / EV_SW(5)
```

**副作用（顺带修好）**：心跳从「每 60 个 tick」改成「每 30s 墙钟」——因为 select 有输入时会立即返回，tick 计数会让循环转速失控、日志被刷屏（原日志里心跳 3 秒一条）。

**排查工具**：`diag.sh --screen` 的【5】会采样 3 秒，逐设备打印事件类型统计与「真实操作数」，直接指出哪个设备在发噪声。

## 五、真机排错

### 5.1 ★ 「设置可以保持了，但设置不生效」

这是一类**独立**的问题：UI 能选、能回显、状态文件也写进去了（说明读/写契约都对了），
但**到点屏幕不黑**。定位按下面顺序查——每一步都有对应日志关键字：

| 排查点 | 日志关键字 | 若缺失/异常的处置 |
|---|---|---|
| ① 空闲监视线程是否起来了 | `[off_time] 空闲监视启动: blank 路径=... 当前档位=Ns` | 没有这行 → 中间件版本旧 / `start_idle_monitor` 未调用 |
| ② 有几个 framebuffer | `[off_time] ⚠ 检测到 N 个 framebuffer，将按【DSI 优先】自动选屏` | 多条 `★选中 / 连接器=...` → 核对选中的是不是小屏 |
| ③ 输入源是否找到 | `[off_time] 空闲监视输入源: [...]` 或 `xprintidle` | 都无 → `⚠ 无可读输入设备也无 xprintidle`，会**只保存不熄屏** |
| ④ blank 路径是否存在 | 同上（`blank 路径=None` 则是问题） | `ls /sys/class/graphics/fb*/blank`；不存在则硬件不支持 |
| ⑤ 是否真的走到熄屏 | `空闲 Ns ≥ Ms → 熄屏（✅ 已确认写入并回读生效）` | 出现 `✗ ...熄屏【未生效】` → **写去了错误的 fb**，见 §5.4 |
| ⑥ 线程是否还活着 | `[off_time] 心跳: 档位=Ms 已空闲=Ns 黑屏中=...`（每 ~30s） | 无心跳 → 线程已死，回传日志 |

**最常见三种原因：**

1. **档位与等待时间理解偏差**——设「2 分钟」却只等了几十秒。日志里 `已空闲=Ns` 会如实显示。
2. **输入设备读不到**（非 root 或触摸被 X 独占）→ 走到「只保存设置，不实际熄屏」分支。
   - 处置：确认中间件以 root 运行；或 `apt install -y x11-utils` 用 xprintidle 兜底。
3. **写去了错误的 framebuffer** → 详见 §5.4。

### 5.4 ★★★ 「日志说熄屏了，但屏幕依旧亮」（本机实测）

**症状**（真机日志实录）：
```
[off_time] 空闲 30s ≥ 30s → 熄屏（已写入）        ← 说成功了
[off_time] 心跳: 档位=30s 已空闲=33s 黑屏中=True  ← 内部也认为黑了
但屏幕依旧亮                                       ← 实际没黑
```

**根因**：写到了**错误的 `fb*/blank`**。本机有多个 framebuffer，
`fb0` 不是小屏；写它**不报错、回读值也变**，但小屏纹丝不动。

**判定**（两条铁证同时出现即可确诊）：
- 日志有 `熄屏（已写入）` / `黑屏中=True`，**但旁观屏幕仍然亮**；
- 启动段 `⚠ 检测到 N 个 framebuffer`（N > 1）。

**处置**：

```bash
# 1) 先找出小屏是哪个 fb（认分辨率，不认编号）
for fb in /sys/class/graphics/fb[0-9]*; do
  echo "$(basename $fb): $(cat $fb/virtual_size 2>/dev/null)  $(cat $fb/name 2>/dev/null)"
done
# 看到 376,960 或 960,376 的那个就是小屏

# 2) 逐个手测，用【肉眼】确认哪个能让屏幕黑（回读值不可信！）
sudo bash tools/diag.sh --screen    # 跑【7】逐个 fb 测试熄屏一节
```

中间件已内置三级策略（自动选屏 → 回读校验 → 遍历候选 → 背光兜底），
**升级后无需手工指定**。若仍不生效，日志会打出
`✗ 所有屏控通道均失败`，此时把 `diag.sh --screen` 的【1】【7】【8】三节输出回传。

### 5.2 诊断脚本


### 5.3 复测步骤（推荐）

1. 覆盖最新 `middleware.py` + `data-mapping.json`，重启服务。
2. 开日志：`journalctl -u hiksemi-sub -f`。
3. 确认启动行有 `[off_time] 空闲监视启动: ...`（无 → 版本没更新成功）。
4. 设「30 秒」，**不触碰屏幕**等 35 秒 → 应看到 `空闲 3Xs ≥ 30s → 熄屏（已写入）`，屏幕黑。
5. 触摸屏幕 → 应看到 `检测到输入 → 亮屏（写入成功）`，屏幕亮。
6. **连续测 3 轮**，确认每轮都稳定（尤其第 2、3 轮）。
